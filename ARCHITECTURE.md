# Architecture

```
browser (three.js, one bundle)                     server (Node 20, Express)                      SQLite (better-sqlite3)
client/src/main.js  ── HTTP heartbeat (adaptive) ─▶ server/core/routes.js (route table + dispatch) ─▶ server/core/schema.js
  ui.js, interior.js ─ JSON actions ─────────────▶   core/economy.js  jobs, shops, housing, bank   ledger_tx / ledger_entries (append-only)
  net.js  ◀── optional WebSocket push (/ws) ──────    core/social.js   presence, knock, DM, travel, land   accounts (balances)
  ads-client.js ── viewability *evidence* ───────▶   core/world.js    presence, trail sanity, heartbeat   property_*, knocks, land_plots, shifts
                                                      core/ads.js      slots, moderation FSM, impressions   ad_* tables
                                                      core/ledger.js   double-entry money
```

## Principles
1. **Server-authoritative.** The client never says "I earned ₦X" or "I saw this ad N times". It sends intent (start shift, buy item, travel to place P by mode M) or evidence, and the server decides with its own clock, its own copy of the city, and its own copy of the player's position.
2. **Money is a double-entry ledger.** Every ₦ movement is a transaction of balanced entries between accounts (user cash, user savings, and named system accounts such as `sys:faucet_jobs`, `sys:sink_shops`, `sys:sink_transport`). Ledger tables are append-only (SQLite triggers refuse UPDATE/DELETE). Idempotency keys make retries safe. `checkInvariants` proves all transactions sum to zero and no balance is negative; the admin overview shows it, and tests assert it after almost every economy action.
3. **Data-driven world.** `server/config/cities/lagos-mainland.json` (generated by `tools/gen-city.mjs`) lists roads, buildings, houses, shops, jobs, billboards, plots, spawns and traffic loops. Server and client both read it; adding a district is data, not code. `core/city.js` derives `places` (tap targets and the only legal travel destinations).
4. **Cheap realtime: HTTP heartbeat.** Each client posts its recent movement trail (samples with ages) every 1.5–20 s; the server clamps speed and bounds, stores a short trail per player, and returns nearby players' downsampled trails. The client renders ghosts ~1.1 s in the past and interpolates. The interval is load-adaptive (`balance.heartbeat` ladder by CCU). WebSocket is only an optional nudge for notifications and knocks.
5. **Portable core.** `core/*` never touches `fs`, `crypto` or Express. They get a `platform` (hashing, hmac, random) and a `db` handle from the host, so the same core can run in Node (production), in tests (`:memory:`), and later behind Postgres or in a browser worker (sql.js) for a static demo.
6. **Ads are measured, not asserted.** The server decides which creative is on a board in each 10 s rotation window (deterministic from time and the assignment list), so it can validate evidence: ≥50% of pixels visible for ≥1 s continuous, board within 90 m of the server-known position, evidence fresh, one count per window, per-user rate limits. Filtered claims are kept with reasons and shown to advertisers.

## Features added in the "section 10" pass
- **Travel:** `GET /api/travel/quote`, `POST /api/travel`. Fare = (base + perM × distance) × rush multiplier; the server charges, moves the player, and writes a timed two-point trail so everyone else sees the vehicle move. Only known `places` are valid.
- **Shop channels and hours:** `shops.channels` multipliers, `shops.hours` on the game clock; delivery is allowed anywhere.
- **Houses:** presence is computed (`home` when the owner is inside their own interior and heartbeating, `online` if heartbeating elsewhere, else `away`). Knock flow is a small state machine in `knocks` (pending → accepted/declined/expired/cancelled/ended) with cooldown after a decline, a guest cap per home tier, and a 10-minute visit permit that gates `GET /api/property/:id/interior` for non-owners.
- **Buy mode:** furniture has `w×d`, `layer` (floor items may sit under objects), position and rotation. The server validates bounds, the reserved bed and doorway rectangles and overlaps; clients mirror the same rule for the green/red ghost. Moves are free, sells refund 50%.
- **Land:** `land_plots` stores purchase price and time; value = paid × (1 + weekly/7)^(days). `tickLand` rolls the omo-onile risk once per land-day per plot (rng injectable in tests) and charges a levy only if the owner can pay.
- **Work task:** server creates a target and a start time; the bar position is a triangle wave of server time, so the client only animates; the server judges the stop request on its own clock.

## Phase 2 additions
- **Trust and safety** (`server/core/filter.js`, `safety.js`). Text screening is token-based with leetspeak/spacing/masking normalisation, so "grape" and "class" pass while `sh1t`, `f u c k`, `f@ck` fail; links, e-mails and phone numbers are refused in public text (house names, chat, DMs, room chat, ad headline/brand). `reports` holds one row per reporter per target (UNIQUE), with a snapshot of what was reported; the admin queue groups by target, shows reasons/counts, and resolves with `dismiss | remove | remove_and_mute` (reset house name, delete message, take an ad down) plus an `audit_log` row. Auto-escalation: 3 distinct reporters hide a house name pending review; 3 reporters on one player's chat pause their chat for 10 minutes. `user_blocks` stores mute (you no longer see them) and block (mute + no DMs, knocks, table seats, ghosts both ways). Per-user limits go through the shared `Limiter`: chat/min, DM/min and per recipient, duplicate-text window, knocks/min and per house, reports/hour, table sits/min.
- **Schema migrations** (`schema.js: migrate()`): idempotent `ALTER TABLE ... ADD COLUMN` so existing databases keep working.
- **Venues** are data (`city.venues` generated by `tools/gen-city.mjs`): door position, hours, and stations (`eat`, `game`, `board`, `poster`, `tv`, `car`). `venues.js` enforces proximity and hours, tracks who is inside (`world.players[].venue`), and clears it when you walk away. The client draws a small 3D room (`client/src/venue.js`) with tappable stations and a strip of station buttons (also the keyboard/touch-friendly path).
- **Table games** (`games.js`, `games/whot.js`, `games/ludo.js`). Engines are pure functions with injected randomness. A match is a row in `game_matches` (JSON engine state; `p1` = host) plus one `game_players` row per seat (Whot 2, Ludo 2 to 4; `out=1` once someone resigned or timed out of a live game); the server validates every move, never sends the market or the opponent hand, enforces a 90 s turn clock (lazy: evaluated on every read plus a 30 s tick; a timeout forfeits), and pays out through the ledger. Stakes are held in `sys:escrow_games` (balanced double entry; winner gets the pot, draws and cancels refund, no rake). Guests and brand-new accounts can only play friendly; at most 5 staked games per pair per day (anti wash-trading). Weekly scoreboard = `game_scores` keyed by Monday-based week. **Decision (Sherif, 9 Oct 2026): Whot plus Ludo as the single extra turn-based game**, order of later games in `11_next_steps.md` (Dominoes, Draughts, Ayo, table football last). Ludo rules are documented at the top of `games/ludo.js`: 52-cell ring, 4 tokens each, 6 to leave base, a 6 rolls again (third six lost), exact roll to finish, capture off the safe cells (start cells + stars), no blocks; the server rolls the die with the injected RNG and clients only send `roll` or `token`. Ludo tables wait for the host's Start (or fill at 4); the pot is `stake x players`, paid to the winner; resigning or timing out removes your tokens and your stake stays in the pot, last one standing wins; an action cap ends endless games (most progress wins). An Ayo engine was prototyped before this decision and has been **removed from the app** (git tag `ayo-prototype`) so it can be restored when its turn comes.
- **Practice bot** (`practice-bot.js`): labelled `@Practice_Bot`, joins only friendly tables, never moves money, never scores. On by default outside production (`PRACTICE_BOT=0` disables) so one person can try the tables.
- **Cars** (`cars.js`): four fictional models with ESTIMATE prices, a 3-slot garage, one active car. The `car` travel mode is now your active car (or a "borrowed car" with a per-trip tip, higher cost and slower): fare = fuel per metre (× rush), seconds = distance / speed, and a mood bump per nice ride (3-minute cooldown). Resale = paid × max(floor, 1 − first-drive-off − per-day × age), credited from a system account; net worth counts cars at resale value.
- **Mood** is a third need (0–100) that drifts to a baseline; games, TV, love, nice cars and repainting raise it; mood ≥ 75 adds a small shift-wage bonus.
- **Homes** (`homes.js`): wall/floor colours (₦ ESTIMATE per repaint, a ledger sink), "Love your house" (once per guest per home per day, persistent count, notification), guest actions (greet, hype, sofa and TV only if those items are placed, with cooldowns), room chat (filtered, rate-limited), host can ask a guest to leave; the room feed is polled every 2.5 s and respects mutes.
- **Static demo** (`demo-static/`, built by `tools/build-demo.mjs`): the *same core* runs in the page. `server/lib/sqljs-adapter.js` makes sql.js look like better-sqlite3 (prepare/run/get/all, exec, nested transactions via savepoints); `demo-src/entry.js` supplies a browser platform (sync SHA-256/HMAC, bcryptjs), replaces `fetch('/api/...')` with a local call into `dispatch`, serves ad creatives from blob URLs, and starts bots and the practice bot. The asm.js build of sql.js is used so nothing needs a `.wasm` fetch, which `file://` forbids.

## Known limits (see ../11_next_steps.md)
SQLite is single-writer: fine for a demo or a few hundred concurrent players on one box; Postgres is the production target and the data layer is kept narrow for that. Movement validation is a speed/bounds clamp, not full physics.
